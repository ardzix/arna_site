# Arnatech HTTPS-origin ownership proof (DRAFT)
Only existing custom domain 174 for canonical arnatech.id, Arnatech tenant 85 and its exact organization. The proof is authority to serve one short-lived value on the canonical HTTPS origin. It does not prove ownership of Vercel's team/account/project; separately record the verified dashboard mapping if required. No Vercel access credential, DNS/TXT changes, new public ownership-write API, JWT trust, or user/provider configuration change is included.

## Release gates and operator sequence
1. Confirm separate production approval for challenge publication and routing, independently review both exact artifacts. Keep `DOMAIN_HTTPS_PROOF_ENABLED`, `DOMAIN_HTTPS_CHAT_ROUTING_ENABLED`, `ARNATECH_BNK_DOMAIN_PROOF_ENABLED`, and all website chat flags off initially; validate exact-image Jenkins production rollback and deployed baseline before release.
2. Verify an attributable, authorized ArnaSite operator context. Supply a dedicated high-entropy `DOMAIN_HTTPS_RECEIPT_KEY` and `DOMAIN_HTTPS_PROOF_OPERATOR_ID` through immutable managed runtime (not reviewer chat, logs or CLI arguments). This is a signer for this exact workflow, not a Vercel credential. Verify existing routing and unrelated apps after the draft's additive audit-table migration. No data migration rewrites any domain.
3. From that operator boundary, run bounded `verify_arnatech_chat_domain --issue-challenge PRIVATE_FILE` with an OS deadline (for example 35 seconds) and operator-owned local directory. It saves a mode0600 file without overwrite/symlinks and writes no DB/site record. The manifest is signed to domain/tenant/org/operator and the current pending-state hash. The separately stored public `publish_value` is the only field to send through the approved production publishing channel. Never publish, log, email, or paste the manifest/signing key/receipt into chat. Max challenge lifetime 15 minutes.
4. Publish just that `publish_value` in `ARNATECH_BNK_DOMAIN_PROOF_VALUE` with `ARNATECH_BNK_DOMAIN_PROOF_ENABLED=true` on the production site only. Explicit verified public-origin admission and the fixed HTTPS host/path are required; Preview/aliases stay dark. Do not activate Chat Arna. Keep temporary proof environment values separate from search/runtime flags. Verify GET behavior and raw response shape in the actual Vercel production runtime.
5. In the same operator boundary use `--challenge-file PRIVATE_FILE` for read-only proof, optionally `--write-receipt PRIVATE_FILE` for private 120-second apply receipt, then only with authorized operator write use `--challenge-file PRIVATE_FILE --apply-receipt RECEIPT_FILE`. The verifier resolves one fixed DNS name, rejects private/special/mixed addresses, pins the selected numeric endpoint, checks TLS trust and hostname/SNI and exact no-store text. It does not follow redirects, uses no ambient proxy or bearer, has a bounded body/socket timeout and must run under the OS deadline to include DNS/slowing peers. The apply re-fetches the same evidence, then uses tenant-before-domain locks, rechecks expiry and all pending/actor/config binding, and writes domain and immutable audit in one transaction. Reuse is rejected after consumption. Provider control can change after network observation; there is no continuous or distributed ownership guarantee.
6. Disable/remove the public temporary proof value and signing-authority enablement, remove the private files, and verify the route 404s. If accepted for controlled launch, enable the separate apex-only `DOMAIN_HTTPS_CHAT_ROUTING_ENABLED` and check that the resolver returns only the approved current CRM tenant. Check CRM entitlement and approved isolated inbox acceptance; only then enable Arnatech web Chat Arna. Other same-org inboxes are not accepted for this apex.
7. Soft rollback is website chat off and apex-only chat-routing off. Keep forward schema/audit and other tenant routes intact. CRM context cache can survive only its configured bounded TTL; recheck live after that. Never reverse/drop the audit schema as normal rollback.

This branch was designed and tested with synthetic HTTPS/provider inputs and a disposable PostgreSQL fixture. No challenge was actually published and no live proof, credentials, deployment or production data action occurred.
